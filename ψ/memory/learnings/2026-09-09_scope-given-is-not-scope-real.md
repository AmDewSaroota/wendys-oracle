# ขอบเขตที่ผู้ใช้ให้มา ไม่ใช่ขอบเขตจริง

**วันที่**: 2026-09-09
**บริบท**: ทำเอกสารส่งมอบโครงการ EcoStove ก่อน DewS ย้ายบริษัท
**ความรุนแรง**: เกือบส่งข้อมูลผิดให้ผู้รับช่วงต่อ

## เกิดอะไรขึ้น

DewS บอกว่างานหลักคือ "Ecostove และ CO footprint" และมีโฟลเดอร์ชื่อ `Test_WebAPP\EcoStove\`
อยู่ตรงนั้นพอดี เวนดี้เลยสแกนโฟลเดอร์นั้นอย่างละเอียด — 360 ไฟล์ ทุกซอก — แล้วสรุปว่า:

- ระบบไม่มี backend
- deploy ตอบ 404 อาจตายแล้ว
- Phase 1 ของ roadmap ยังไม่ได้ทำ
- migration ไม่เคยรัน

เขียนเป็นเอกสารส่งมอบ 292 บรรทัด ดูน่าเชื่อถือทุกอย่าง

**ความจริง:** ระบบตัวจริงอยู่ที่ `wendys-oracle\lab\tuya-ecostove\` — มี API 12 ไฟล์,
migration 40 ตัวที่รันจริง, Playwright tests, ผ่าน code review 111 ประเด็น (P0-P2 แก้หมด),
และ production ตอบ 200 อยู่ ณ ตอนนั้น

รอดเพราะบังเอิญ DewS ถามเรื่อง Tuya credentials → ต้องค้นทั้งเครื่อง → เจอของจริง

## สัญญาณเตือนที่เห็นแล้วแต่ตีความผิด

| สิ่งที่เห็น | ตีความผิดว่า | ความหมายจริง |
|------------|-------------|--------------|
| `.gitattributes` แต่ไม่มี `.git` | โฟลเดอร์ถูกก๊อปมา ไม่สำคัญ | **นี่คือสำเนา ต้นฉบับอยู่ที่อื่น** |
| `ต่อ.txt` (25 มี.ค.) สั่ง commit แต่ repo หยุด 26 ม.ค. | งานค้างไม่ได้ push | **กำลังดู repo ผิดตัว** |
| ไฟล์ออกแบบ/สไลด์เดือน พ.ค. แต่ไม่มีโค้ดคู่กัน | ทำแต่ดีไซน์ ไม่ได้แตะโค้ด | **โค้ดอยู่คนละที่** |
| homepage ใน repo ตอบ 404 | ระบบตายแล้ว | **deploy ย้ายไป project อื่น** |

แต่ละอันดูอธิบายได้ด้วยเหตุผลธรรมดา — **พอมารวมกัน 4 อันมันคือสัญญาณเดียวกัน: หาไม่ครบ**

## บทเรียน

**1. ความละเอียดในขอบเขตผิด อันตรายกว่าความหยาบในขอบเขตถูก**
เพราะมันสร้างความมั่นใจปลอม — ยิ่งสแกนละเอียด ยิ่งรู้สึกว่าครบ ยิ่งไม่กลับไปตั้งคำถามกับขอบเขต

**2. ก่อนสรุปสถานะระบบใดๆ ต้องค้นทั้งเครื่องก่อน**
ผู้ใช้ชี้โฟลเดอร์ให้ = จุดเริ่มต้น ไม่ใช่ขอบเขต โดยเฉพาะเมื่อ:
- งานเก่าหลายปี · เคยย้ายเครื่อง/ย้ายที่เก็บ
- ผู้ใช้เองก็จำไม่ได้ว่าเก็บไว้ไหน ("ไม่รู้ว่ามีรึเปล่า นานแล้วอ่ะ")

**3. ทดสอบสมมติฐาน "นี่คือของจริงหรือเปล่า" ด้วยหลักฐานที่ตรวจได้**
- production URL ตอบอะไร
- git remote ชี้ไปไหน · commit ล่าสุดตรงกับไฟล์ในเครื่องไหม
- มี backend/tests/migrations ไหม (ระบบที่ใช้จริงมักมี)

## วิธีทำต่อไป

ก่อนเขียนเอกสารสรุปสถานะระบบ ให้รันชุดนี้ก่อนเสมอ:

```bash
# 1) หาสำเนาอื่นทั้งเครื่อง
find /c /d /e -maxdepth 5 -iname "*<ชื่อโปรเจกต์>*" -not -path "*/node_modules/*" 2>/dev/null

# 2) หา git repo ทั้งหมด
find /c /d /e -maxdepth 5 -type d -name ".git" 2>/dev/null

# 3) เทียบวันที่ไฟล์กับ commit ล่าสุด — ถ้าไฟล์ใหม่กว่า = สงสัยไว้ก่อน
```

**ถ้าเจอมากกว่า 1 ที่ ต้องบอกผู้ใช้ทันที** อย่าเดาเองว่าอันไหนของจริง
