## Honest Feedback

**Friction 1: Context overflow recovery tax.** Even with a perfect summary, there's a startup cost to re-reading code sections and rebuilding mental models. The summary told me *what* to fix but I still needed to *see* the code to understand *how*. This session spent about 40% of its time just reading and verifying before making any changes. Context overflow is expensive.

**Friction 2: No way to verify DB state.** I created mock data SQL but have no way to confirm what data actually exists in Supabase right now. Are there already stove types from DewS manually adding them? Will the ON CONFLICT clause handle duplicates correctly? I designed the SQL defensively (INSERT ON CONFLICT DO NOTHING, UPDATE WHERE stove_id IS NULL) but uncertainty remains.

**Friction 3: Preview-map.html exists as a separate copy.** The deep map logic exists in both index.html and preview-map.html with slightly different implementations. Any change to the map must be applied to both files — easy to forget. This is technical debt that should eventually be refactored into shared code, but under the Dashboard Full Lock policy, that's not something we should touch right now.

## Lessons Learned

- **When fixing a data model change, grep for ALL references across ALL files** — not just the main file. preview-map.html would have been a silent regression.
- **Context overflow summaries should always include "NOT YET DONE" items with file paths and line numbers** — this session's summary did exactly that, making recovery fast.
- **Mock data with MOD() creates deterministic variety** — better than random, easier to debug, reproducible across runs.
