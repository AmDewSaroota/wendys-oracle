## Honest Feedback

**Friction 1 — Direction กับ system-demo ผิดตั้งแต่ต้น**: หนูออกแบบเป็น "interactive scenario player" (sidebar + คลิกดู state) ทั้งที่ DewS ต้องการ "realistic dashboard mockup" (เหมือน mockup-narrative.html) — ถ้าเช็ค reference file ของ DewS ก่อนเริ่ม จะไม่เสียเวลาทำใหม่ทั้งไฟล์ บทเรียน: ก่อน build อะไรใหม่ ดูว่ามีของเก่าใน repo หรือเปล่า

**Friction 2 — Tone polish หลายรอบ**: DewS ทักหลายจุด ("ขีดจำกัด", "ตัด post", "sensor saturation", หางเสียง) ที่จริง ๆ ถ้าหนูทำ tone audit หลังเขียนเสร็จก่อน present ก็จะลด feedback loop ได้ — การเขียนแบบ technical-mix-Thai ของหนูบางครั้งห้วน/jargon เกินไปสำหรับ formal Thai workshop

**Friction 3 — Memory bloat**: บันทึก feedback memory 11 ตัวใน session เดียว (each เป็น separate file) — MEMORY.md index ยาวขึ้นเรื่อยๆ ครั้งหน้าควรพิจารณา consolidate feedback memories ตามหัวข้อใหญ่ (เช่น "teaching content rules" รวม 4-5 rules ใน 1 ไฟล์) แทนแยกทีละไฟล์

## Lessons Learned

1. **หลักการ vs สไตล์** — เอกสารสอนคนนอก = universal principles only · DewS-Oracle workflow = ไปอยู่ใน Oracle Onboarding doc แยก
2. **ก่อน build ใหม่ scan ของเก่าก่อน** — ถ้าใน repo มี mockup-narrative.html, training.html, slides.html อยู่แล้ว ใช้เป็น base ดีกว่าทำใหม่ทั้งหมด
3. **Image placeholders ต้องมี aspect ratio จริง** — 4:3 / 16:9 / 3:4 — ไม่ใช่ flexible bar ที่ดูไม่เป็นรูป
4. **Tone audit ก่อน present** — scan jargon + ห้วน wording ก่อนส่งให้ DewS ดู
